Project Proposal: PrismForge — Personal AI-Powered Research Writing Studio
A local-first, offline-capable LaTeX editor, scientific PDF workspace, and AI-assisted academic writing environment
1. Executive summary
PrismForge is a personal research-writing application designed to provide an integrated environment for writing, editing, compiling, reviewing, and formatting scientific and academic papers. Inspired by the workflow of OpenAI Prism, the project aims to bring together a professional LaTeX editor, side-by-side PDF preview, AI-assisted manuscript editing, reference management, research quality checks, and document version history in one application.

Unlike cloud-first academic writing platforms, PrismForge will prioritize local storage, offline document editing, and local LaTeX compilation. Research files, source code, figures, bibliography files, and generated PDFs will remain on the user's computer by default. Online AI assistance will be optional and accessed through the user's own OpenAI API key, with explicit control over which manuscript content is submitted.

The application will initially target a Windows 11 desktop environment while also supporting a locally hosted web interface. Both modes will share a common codebase and project format, reducing duplication and keeping future development manageable.

The main objective is to build a practical research tool for an individual researcher, not a commercial multi-user platform. Development will proceed incrementally, beginning with the essential editor and PDF workflow and expanding into intelligent editing, automated formatting, and advanced research support.
2. Problem statement
Academic and technical writing often requires switching between multiple tools for source editing, PDF inspection, reference management, grammar correction, LaTeX debugging, and document formatting. This fragmented workflow can waste time and introduce inconsistencies into research manuscripts.

Common challenges include:
- Editing LaTeX source while repeatedly switching between the editor and compiled PDF.
- Identifying compilation errors, missing references, broken citations, and formatting problems.
- Correcting academic language without unintentionally changing technical meaning.
- Maintaining consistency across a manuscript's abstract, methodology, equations, results, discussion, and conclusion.
- Applying journal-specific templates and formatting requirements.
- Managing revisions and recovering earlier versions after extensive edits.
- Working offline or maintaining control over sensitive unpublished research.
- Using AI assistants that do not have sufficient project context or cannot safely apply changes to the original files.
PrismForge will address these problems by providing one coordinated workspace with local document management, deterministic validation, and optional AI-assisted editing.
3. Project vision and objectives
Vision
To create a reliable, lightweight, privacy-conscious research-writing environment that makes academic LaTeX authoring, manuscript review, and PDF production easier for personal use.
Primary objectives
1. Build a professional LaTeX code editor with syntax highlighting, autocomplete, project navigation, and autosave.
2. Integrate local LaTeX compilation and a synchronized, side-by-side PDF viewer.
3. Add optional GPT-powered proofreading, academic rewriting, LaTeX troubleshooting, and formatting assistance.
4. Develop automated checks for bibliography consistency, cross-references, manuscript structure, and common formatting problems.
5. Support reusable academic templates and exportable research projects.
6. Maintain local snapshots, change comparisons, and reliable recovery mechanisms.
7. Support offline work without requiring a remote account or cloud document storage.
8. Provide desktop and local web interfaces using a shared application architecture.
Success criteria
The project will be considered successful when a user can open an existing research paper, edit multiple files, compile a PDF, identify and repair errors, request an AI-assisted revision, inspect the proposed changes, and export the final paper without leaving the application.
4. Project scope
PrismForge will be developed as a local-first, single-user application. It will not initially require accounts, remote databases, cloud hosting, or a collaboration server.
4.1 In scope
- Local project creation and importing existing LaTeX projects.
- Editing .tex, .bib, and related text files.
- Managing figures, tables, and other project assets.
- Local compilation and live PDF preview.
- GPT API integration for user-requested writing and debugging assistance.
- AI-proposed edits with manual approval.
- Basic and advanced manuscript validation.
- Bibliography and citation management.
- Journal and academic document templates.
- Local revision history and backup.
- Desktop packaging and localhost web access.
- Offline operation for local functionality.
4.2 Out of scope for the initial release
- Public cloud hosting or a multi-tenant SaaS service.
- Real-time multi-user collaboration.
- Training a custom large language model.
- Guaranteeing scientific correctness or plagiarism-free writing.
- Automatically submitting papers to journals.
- Guaranteed detection of AI-generated text.
- Fully automated verification of every research claim.
- Complete feature parity with commercial research platforms.
These features may be considered later, but they are not necessary to deliver the core product.
5. Target users and use cases
The initial target user is an individual researcher or student writing technical papers, dissertations, term papers, and journal manuscripts.

Typical use cases include:
- Writing a research paper using LaTeX.
- Revising a manuscript after supervisor or reviewer feedback.
- Fixing compilation errors before submission.
- Checking figure numbering, equation references, and bibliography consistency.
- Improving academic tone while preserving technical terminology.
- Comparing revised and original manuscripts.
- Converting an existing paper to a supported journal template.
- Preparing a clean, reproducible project archive for future work.
The application will be particularly useful for research involving equations, algorithms, tables, figures, citations, and technical terminology.

7. Detailed feature specifications
7.1 LaTeX editor and workspace
The editor should provide a familiar code-editing experience rather than a plain text area.

Required capabilities:
- Syntax highlighting for LaTeX commands, environments, comments, math, and citations.
- Autocomplete for common commands, environments, labels, and citation keys.
- Multi-file tabs and a navigable project explorer.
- Search across the current file and, eventually, the entire project.
- Line numbers, bracket matching, code folding, and snippets.
- Automatic saving with clear recovery behavior.
- A resizable editor and preview layout.
- Keyboard shortcuts for save, compile, search, and navigation.
- Jump-to-definition support for labels and references where feasible.
The editor must not silently rewrite user content or normalize the entire source file without permission.
7.2 Compilation and PDF synchronization
The compilation service will execute a local LaTeX engine and display the generated PDF.

It should:
1. Save pending changes before compilation.
2. Run the configured compiler in the project directory.
3. Capture logs, errors, and warnings.
4. Detect whether the PDF was successfully generated.
5. Refresh the preview only when a new valid output is available.
6. Preserve the last successful PDF when a later compilation fails.
7. Support multiple compilation passes when references or citations require them.
8. Provide forward and inverse source/PDF navigation where the selected tools support it.
A successful source edit must not be mistaken for a successful compilation. The application should clearly distinguish the last successful PDF from the current source state.
7.3 GPT-powered academic assistant
The AI assistant will use the OpenAI API through a secure local application service. The model should be configurable rather than hard-coded, allowing supported models to change as the API evolves.

Available actions should include:
- Proofread grammar and spelling.
- Improve academic clarity and tone.
- Reduce redundancy.
- Expand a paragraph with user-supplied supporting information.
- Improve transitions between sections.
- Explain equations and LaTeX commands.
- Suggest clearer figure captions and table descriptions.
- Draft a response to supervisor or reviewer comments.
- Compare selected text against surrounding manuscript context.
- Suggest structural improvements across the paper.
AI output must be treated as a proposal, not authoritative truth. It should never fabricate experimental results, references, or research claims.
7.4 AI-assisted LaTeX debugging
The user should be able to select a compiler error and request a diagnosis. The application can provide the relevant error log, nearby source lines, document class, and selected package information to the AI.

The assistant should return:
- A plain-language explanation.
- The likely cause.
- A proposed minimal correction.
- Potential side effects.
- A way to compare and apply or reject the patch.
- An optional recompilation after approval.
Compiler diagnostics and deterministic checks should be used first where possible. GPT should supplement those checks rather than replace them.
7.5 Formatting and research quality checks
Formatting checks will be divided into two categories.

Deterministic checks can be automated reliably when the source contains sufficient information:
- Undefined labels and unresolved references.
- Duplicate labels and duplicate citation keys.
- Unused or missing bibliography entries.
- Unresolved placeholders such as TODO or FIXME.
- Missing figure files and common asset path errors.
- Overfull and underfull box warnings from compiler logs.
- Missing captions or labels in configured figure and table patterns.
- Inconsistent heading or abbreviation patterns.
AI-assisted checks will provide suggestions for issues requiring interpretation:
- Repeated arguments or redundant paragraphs.
- Inconsistent terminology between sections.
- Weak transitions and unclear methodology descriptions.
- Possible discrepancies between results and discussion.
- Unsupported statements that may require citations.
- Possible conflicts between the abstract and conclusion.
AI checks will be labeled as suggestions and will not claim that a paper is scientifically valid simply because it passes them.
7.6 Journal templates and format conversion
The application should maintain a library of user-accessible templates and associated validation rules.

Initial targets:
- Standard academic article.
- IEEE-style paper.
- Elsevier-style paper.
- A customizable generic research manuscript.
Each template may specify a document class, required packages, bibliography configuration, title structure, and supported formatting checks.

Format conversion should be implemented through explicit transformations and configuration changes. It must not blindly replace every LaTeX command across the manuscript. Some publishers require proprietary or separately downloaded class files, so those must be supplied and licensed appropriately by the user.
7.7 Reference management
The reference module will focus initially on BibTeX, since it integrates naturally with conventional LaTeX projects.

Features include:
- Import and edit .bib files.
- Search by citation key, author, title, and year.
- Detect duplicate entries and missing required metadata.
- Inspect where citation keys occur in the source.
- Flag source citations with no corresponding bibliography entry.
- Help prepare BibTeX records from verified metadata.
- Export the updated bibliography.
Optional online discovery and Zotero synchronization can be added after the local workflow is stable. Offline checks can validate structure and consistency, but cannot guarantee that a publication exists or that a citation genuinely supports a claim.

The architecture should separate the user interface, local file operations, compiler execution, AI integration, and project metadata. This will make the application easier to test and reduce security risks.

8.3 Desktop and web execution models
Desktop mode: Tauri launches the interface and exposes carefully restricted commands for reading project files, saving source, compiling documents, and accessing local history.

Local web mode: The frontend runs in a browser and communicates with a local service bound to 127.0.0.1. The service provides the file and compilation operations unavailable to an ordinary browser.

The local service must validate requests, restrict access to configured project directories, and avoid exposing an unrestricted shell or filesystem API.

Both modes should use the same project structure and common application logic. They may use different adapters for filesystem operations and compilation.

9.2 Local database design
SQLite will store application metadata, not the full source of truth for the manuscript.
Table	Purpose
projects	Project name, root directory, main file, template, timestamps
settings	Application preferences and compiler settings
ai_sessions	Local conversation metadata and references to context, when history is enabled
ai_changes	Proposed and applied edits, affected files, status, timestamps
snapshots	Revision identifiers and backup locations
diagnostics	Cached compilation errors and validation results
references_cache	Optional local cache of imported reference metadata

The exact schema can be finalized during implementation. Avoid storing API keys in ordinary SQLite settings; use a secure credential store where available.
9.3 Version history and recovery
The application should take snapshots before major automated edits, template conversions, and user-requested checkpoints.

Each snapshot should record the affected files and a timestamp. The user should be able to compare changes, restore individual files, or recover the complete project to an earlier checkpoint.

For safety, a restore operation must create a recovery snapshot before overwriting current files. Version history is not a substitute for independent backups, so users should also be able to export backups to another location.
10. AI integration design
The AI layer will use a structured request and response workflow rather than unrestricted text replacement.
10.1 Request pipeline
1. The user chooses an AI action and selects the content or context scope.
2. The application gathers only the required source text, relevant context, and optional compiler diagnostics.
3. The local service constructs the API request.
4. The AI returns a proposed edit or diagnosis.
5. The application validates the response format and checks for malformed or incomplete output.
6. The user reviews the changes in a diff interface.
7. Approved edits are applied to the source and saved.
8. The application can run validation and compilation to detect regressions.
10.2 Context management
Context should be configurable at three levels:
- Selection context: Only the selected text and a small surrounding passage.
- Section context: The current section, relevant citations, and selected project conventions.
- Project context: Relevant sections, definitions, notation, and project-wide terminology.
Project-wide context should not mean automatically sending every file on every request. The application should select relevant content, show what will be sent, and allow the user to reduce the scope.
10.3 Proposed AI response format
The AI service should return a structured result containing:
- Action type.
- Original content reference.
- Proposed replacement or patch.
- Explanation of the changes.
- Any warnings or assumptions.
- Whether the result requires user confirmation.
Structured output and local validation reduce the risk of applying malformed responses. The application must also guard against a model accidentally removing citations, changing equations, or altering LaTeX commands.
10.4 Model selection and API configuration
The application should allow a user-configurable model identifier and compatible settings. It must not assume a specific model name will remain available indefinitely.

The user should be able to:
- Enter or update their API credentials securely.
- Test the connection.
- Set a maximum response size and optional spending limits where supported.
- View recent request metadata and estimated usage when available.
- Disable AI access completely.
- Clear locally retained AI history.
A ChatGPT subscription should not be treated as an API key or as automatic authorization to make API requests.
11. Security, privacy, and reliability
Privacy and security must be built into the architecture, not added only before release.
11.1 Data protection
- Store research files locally by default.
- Require an explicit user action before sending content to an online AI service.
- Make the context included in each AI request inspectable.
- Keep credentials out of source code, frontend bundles, logs, and exported project files.
- Provide a clear way to disable network-dependent functionality.
- Use HTTPS for external API requests.
- Keep AI session history optional and locally controlled.
11.2 Compiler and filesystem security
LaTeX compilation can execute commands or invoke external tools depending on the engine, packages, and configuration. Therefore:
- Run compilation with shell escape and unrestricted external execution disabled by default.
- Use a restricted process environment and working directory.
- Apply execution timeouts and reasonable memory or output limits.
- Validate project paths to prevent directory traversal.
- Do not allow a local web endpoint to execute arbitrary commands supplied by a browser request.
- Avoid compiling untrusted projects with unrestricted permissions.
A sandbox is preferable for compiling unknown third-party projects, but even a sandbox must be configured correctly.
11.3 Reliability requirements
The application should:
- Preserve the last successful PDF when compilation fails.
- Recover unsaved content after an unexpected shutdown where feasible.
- Prevent concurrent compilation jobs from corrupting output.
- Avoid silently overwriting external changes to a file.
- Record failed operations clearly.
- Verify backups and recovery behavior during testing.
11.4 Research integrity
The AI assistant must not invent citations, experimental measurements, equations, or conclusions. It should distinguish between a language edit and a change to scientific meaning.

The user remains responsible for verifying scientific claims, citations, publisher requirements, and the accuracy of the final manuscript.

- Keep primary actions accessible: Save, Compile, Preview, AI Assistant, and Export.

13. Development methodology and phased implementation
The project will follow an iterative development process. Each phase must produce a working, testable result before the next phase begins.
Phase 1

Requirements and project setup

Estimated duration: 3–5 days

Define the architecture, create the repository, configure the frontend, establish coding conventions, and prepare a minimal sample LaTeX project.

- Deliverable: Running application shell and approved project structure.



Phase 2

Editor and local project management

Estimated duration: 1–2 weeks

Implement project browsing, file tabs, source editing, saving, autosave, and basic editor preferences.

- Deliverable: Reliable multi-file LaTeX editing.



Phase 3

Compiler and PDF preview

Estimated duration: 1–2 weeks

Integrate the selected LaTeX engine, process logs, PDF.js, compilation status, and error navigation.

- Deliverable: A working offline LaTeX editor with side-by-side PDF output.



Phase 4

AI assistant and safe editing

Estimated duration: 1–2 weeks

Add API configuration, context selection, streaming responses, proofreading, patch generation, and diff review.

- Deliverable: GPT-assisted edits that require approval before application.



Phase 5

Validation, references, and formatting

Estimated duration: 2–3 weeks

Implement compiler-log diagnostics, citation checks, template validation, reference tools, and research quality suggestions.

- Deliverable: A manuscript review toolkit.



Phase 6

History, export, and recovery

Estimated duration: 1 week

Implement snapshots, diff review, rollback, project ZIP export, and backup restoration.

- Deliverable: A recoverable research workflow.



Phase 7

Desktop packaging, web mode, and final testing

Estimated duration: 1–2 weeks

Package the desktop application, implement or finalize local web mode, test disconnected operation, and validate security and recovery.

- Deliverable: A documented, usable personal release.



Estimated total: approximately 8–14 weeks for a substantial first release with part-time development, assuming the core libraries are reused and the scope remains controlled. A small MVP can be completed earlier; the more advanced integrations may take longer.

The phases can overlap where appropriate, but the compiler, file-management, and AI security foundations should be completed before adding extensive automation.
14. Testing and quality assurance
Testing must cover normal use, failure scenarios, privacy boundaries, and compatibility with real research projects.
14.1 Functional tests
- Create, open, edit, save, and reopen a LaTeX project.
- Edit multiple source files and preserve project paths.
- Compile a simple paper and a multi-file paper with citations and figures.
- Display the latest successful PDF and preserve it after compilation failure.
- Detect missing files, broken references, and common compiler errors.
- Request an AI revision, inspect the diff, apply it, reject it, and undo it.
- Export a project and successfully reopen the exported archive.
- Recover from an interrupted editing session.
14.2 AI quality tests
- Preserve \cite, \ref, \label, math environments, and custom macros.
- Check that edits do not unexpectedly remove sections or figures.
- Verify that rejected proposals never modify the source.
- Test malformed AI responses and network timeouts.
- Verify that AI edits can be reverted.
- Use sample manuscripts containing known errors to assess whether the assistant identifies them.
14.3 Offline and security tests
- Disconnect the network and confirm that local editing and compilation still work.
- Verify that AI requests fail clearly without affecting the document.
- Confirm that source content is not sent externally without user action.
- Test invalid project paths and attempts to access files outside the selected workspace.
- Verify that API keys are absent from browser bundles, logs, and project exports.
- Test compiler timeouts and restricted execution settings.
- Restore a backup and verify the integrity of the recovered files.

15. Deployment and installation plan
The application should be distributed initially as a local development build, then as a Windows installer once the core workflow is stable.
15.1 Development environment
The initial development environment will include:
- Windows 11.
- Node.js and npm for frontend tooling.
- Rust toolchain for Tauri desktop development.
- A supported LaTeX compiler and the required packages.
- Git for source control.
- An OpenAI API key configured outside the frontend.
- A local test repository containing representative research papers.
15.2 Installation modes
Desktop installer

The installer should package the desktop interface and required runtime assets. The LaTeX compiler and its packages may be bundled or installed separately, depending on size and licensing.

Local web mode

A local launcher should start the web frontend and its local service, then open the application in the default browser. The launcher should provide a straightforward way to stop the service.

Neither mode requires a public server. The application should not bind its local service to all network interfaces by default.
15.3 Offline preparation
Before using the application offline, the user must install or cache the required compiler, packages, fonts, and runtime dependencies. The installer should identify missing dependencies before disconnecting.

A practical offline acceptance test should start from a disconnected network and verify that a prepared sample paper compiles successfully.
15.4 Updates
Application updates should be separate from manuscript files. Updating PrismForge must not overwrite or migrate research projects without permission. Users should be able to back up their projects before upgrading.
16. Resource requirements and cost estimation
16.1 Hardware
The target environment is a Windows 11 laptop with 16 GB RAM and a modern multi-core CPU. This is adequate for a lightweight editor, local PDF rendering, SQLite, and ordinary LaTeX compilation.

No GPU is required for the initial release because GPT reasoning will run through the hosted API. An optional local AI model would need separate benchmarking before being recommended.

17. Risk analysis and mitigation
Risk	Impact	Mitigation

The highest-priority risks are data loss, unsafe file access, incorrect AI edits, and unreliable compilation. These should be addressed before advanced integrations.

- Local language models for basic offline proofreading.
- Local document indexing and retrieval.
- Hybrid routing that sends only complex tasks to the GPT API.
Advanced reliability
- Property-based tests for automated source transformations.
- More detailed template compatibility checks.
- Optional integration with external power or performance monitoring tools if resource efficiency becomes a specific development goal.
These enhancements should remain modular. They must not compromise the lightweight, local-first character of the application.
21. Final recommendation
I recommend developing PrismForge as a desktop-first, local-first research application with a shared local web interface, rather than beginning with a cloud-hosted platform.

The most important architectural decisions are:
- React + TypeScript + CodeMirror 6 for the research-writing interface.
- Tauri 2 for the Windows desktop application.
- Tectonic initially, with optional TeX Live for broader LaTeX compatibility.
- PDF.js for the side-by-side PDF viewer.
- SQLite and normal local files for project metadata and research documents.
- OpenAI API for optional, context-aware AI assistance.
- Diff-based editing and snapshots to protect the original manuscript.
- A strict offline-first design for editing, compilation, and document validation.
The development order matters: build the editor and compiler first, add safe AI editing second, and implement advanced research tools after the core workflow is stable.

The final goal is not simply to create another LaTeX editor. It is to build a dependable personal research environment in which you can write a paper, inspect the compiled PDF, improve academic language, diagnose technical errors, check formatting, and maintain control over every change—all within one application.
